Section 01

What this tests, in plain words

TorchLean is a neural-network library written in Lean 4. Lean is a proof assistant. It can check a mathematical claim the same way a compiler checks a type. TorchLean uses that ability for two jobs: it trains models like any other library, and it proves things about them.

A typical proof looks like this. Take a trained image classifier. Nudge every pixel a little. Does the answer stay the same? A normal test tries a few nudges. TorchLean bounds all of them at once and reports a fact: for this input, no nudge inside this box can change the answer. That fact is called a certificate.

A certificate is worth nothing if the checker says yes to everything. So this suite does two kinds of work. Eight cases check that correct things are accepted. Two cases feed the checker a broken certificate and demand a rejection. One case records a bug that is still open upstream. One case runs the same training on the graphics card.

Everything runs against your real installed copy at ~/TorchLean inside WSL, at commit 6a5d659. Nothing is mocked.

Section 02

What must already be on the machine

Three things. The suite will not install them for you.

ItemWhyHow to check
Git Bash The terminal you type in. It ships with Git for Windows. Open the Start menu. Type Git Bash. A black window opens.
WSL Ubuntu A real Linux running inside Windows. Lean is built there. Native Windows builds are blocked on this machine, because Malwarebytes deletes lld.exe. Type wsl -l -v. You should see Ubuntu and Running or Stopped.
The TorchLean checkout The source code and its built binaries. It lives at ~/TorchLean inside Ubuntu, not on the Windows disk. Type wsl -d Ubuntu -- ls ~/TorchLean. You should see NN and lakefile.lean.

You do not need to open WSL yourself. The script does that for you.

Section 03

Run the suite

  1. Open Git Bash from the Start menu.
  2. Go to the folder. Type this line and press Enter: 
    cd /c/Users/<you>/Downloads/torchlean_latent
    That is the Git Bash spelling of C:\Users\<you>\Downloads\torchlean_latent. Forward slashes, and /c/ in place of C:.
  3. Start the suite: 
    ./run_tests.sh
    The leading ./ is required. It means "the script in this folder".
  4. Wait. A warm run takes about 48 seconds. The first run of a case can take several minutes, because Lean compiles the code it needs. That happens once.
  5. Read the twelve lines it prints. Every line starts with PASS or FAIL.

Add the graphics-card case

Type this instead:

./run_tests.sh --cuda

This adds case 12. It builds a second, separate copy of the library with GPU support. Expect a long first run. Switching back to the plain ./run_tests.sh afterwards is fast — it was measured at 48 seconds.

Point it at a different checkout

TL_REPO=/home/<you>/TorchLean ./run_tests.sh

Give a Linux path, such as /home/<you>/.... Do not give a Windows path such as C:\.... The default is ~/TorchLean.

What the script does behind the scenes

You start it on Windows. It notices that, and restarts itself inside Ubuntu with wsl.exe -d Ubuntu. Every Lean command then runs on the Linux side. You never see the switch. This matters only if you edit the script — see Notes for editors.

Read the result

PASS  01-tensor-types        Float/ℚ/Int/Float32/IEEE32Exec printed; Tensor ℝ refused
PASS  02-autograd-closed     grad1(mean(x^2)) = [0.500000, -1.200000] exact
PASS  03-train-typedgraph    loss 1.349908 -> 0.002521 (falls)
PASS  04-train-autompg       loss 0.264566 -> 0.057793, trainlog JSON written
PASS  05-ibp-lowering        18 IR nodes, box [1.904000, 2.256001]

PASS  07-margin-cert         349/360 nominal, 318/360 certified
PASS  08-abcrown-leaf        1 leaf checked, ok=1 bad=0
PASS  09-neg-tampered        tampered bounds rejected (mismatch reported)
PASS  10-neg-malformed       truncated artifact rejected at parse time
PASS  11-xfail-pinn-cert     known: bundled pinn_cert.json still mismatches

Each line has three parts: the verdict, the case name, and the evidence. The evidence is a real number or a real message taken from the command's own output. The suite never judges a case by its exit code. A program can exit quietly and still be wrong, so the printed output is what counts.

A failing line looks like this. The suite prints the last twelve lines of real output under it, each marked with a |, so you can see what actually happened:

Failing case — example
FAIL  08-abcrown-leaf        leaf artifact check did not report ok=1 bad=0
        | [artifact] Checked 1 leaves: ok=1, bad=0

The last line of a run is the count. The script also sets an exit code: 0 when every case passed, 1 when any case failed. That makes it usable from a build server later, with no changes.

Section 05

The twelve cases, one at a time

The numbers are the case IDs the script prints. They are grouped by the question each group answers.

Group A — Is the maths still right?

01
Accept

tensor-types

lake exe torchlean quickstart_tensors

A tensor is a grid of numbers. TorchLean tracks which kind of number is inside, in the type itself: ordinary Float, exact fractions ℚ, whole numbers Int, and two flavours of 32-bit float.

One kind is special. Tensor ℝ holds real numbers — the mathematician's kind, with infinite precision. No computer can print those. TorchLean must therefore refuse to print it, and tell you to convert first. That refusal is the whole point of the case: the library keeps proof-level maths and runnable code apart, and does not quietly blur them.

Asserts → the IEEE32Exec row prints, and the words "Refusing to print" appear.

02
Accept

autograd-closed

lake exe torchlean quickstart_autograd

Training a network means following gradients — the slope of the error. The library computes those slopes automatically. This case checks the machine against a slope worked out by hand.

The function is the mean of x squared, over n numbers. Its derivative is 2x divided by n. The example uses n = 2, so the two halves cancel and the derivative is simply x. The input is x = [0.5, −1.2], so the gradient must come back as [0.5, −1.2] — the input, reproduced exactly. Any other value means the gradient engine is broken, and every trained model built on it is suspect.

Asserts → the exact line grad1(mean(x^2)) = [0.500000, -1.200000].

Group B — Does training actually learn?

03
Accept

train-typedgraph

lake exe torchlean quickstart_mlp --steps 200 --scalar ieee32-exec --execution typed-graph

A small network trains for 200 steps on toy data. The loss is the error. It must go down.

Two settings make this case interesting. ieee32-exec means the arithmetic follows the IEEE-754 32-bit standard bit for bit, not a loose approximation. typed-graph means the model runs as a checked computation graph rather than step-by-step. Both paths must still learn.

Asserts → the final loss is below the first loss. Observed 1.349908 → 0.002521.

04
Accept

train-autompg

lake exe torchlean mlp --steps 50

The same idea on real data: the Auto MPG dataset, 78 cars, predicting fuel economy. This case reads a file from disk, so it also proves the data path works.

It checks a second thing. The run must leave behind data/model_zoo/mlp_trainlog.json, the training log. The suite deletes that file first, then demands it reappear and be non-empty. A run that trains but writes nothing is only half a success.

Asserts → loss falls (0.264566 → 0.057793) and the log file exists and is not empty.

Group C — Does verification work?

05
Accept

ibp-lowering

lake exe verify -- torchlean-ibp

This is the first half of verification: turn a model into something provable. The network is lowered into an intermediate graph — 18 nodes — and then bounded.

IBP means Interval Bound Propagation. Instead of one input, you feed in a range. Each layer widens or narrows that range. At the end you get a box: the output cannot leave it. Here the box is [1.904000, 2.256001].

The case pins the node count at 18, because a change there means the model was translated differently, and checks that the low end is below the high end. A box with the ends swapped is meaningless.

Asserts → exactly 18 IR nodes, and lo < hi.

06
Accept

cert-accept

lake exe verify -- lirpa-mlp

Here Lean checks somebody else's homework. An outside tool (LiRPA, a Python bound calculator) produced a certificate file with the bounds it claims. Lean does not trust it. It recomputes the bounds itself, then asks one question: do the claimed bounds enclose mine?

Enclosing is what matters, not matching. The outside tool is allowed to be more cautious than Lean. It is not allowed to claim a tighter bound than the maths supports.

Asserts → the message "IBP certificate verified" appears.

07
Accept

margin-cert

lake exe verify -- margin-cert

The headline result, on 360 handwritten-digit images. Two counts come back.

Nominal, 349 of 360. The model gets the answer right on the plain image. That is ordinary accuracy. Certified, 318 of 360. Lean proved the answer cannot change anywhere inside the allowed nudge box. That is a much stronger claim, so the number is lower.

The gap between 349 and 318 is honest. Those 31 images are classified correctly but not provably so. The case fixes all three numbers, because a silent drift in any of them means the certification pipeline changed.

Asserts → exactly 360 / 349 / 318.

08
Accept

abcrown-leaf

lake exe verify -- abcrown-leaf

α,β-CROWN is a well-known external verifier. It splits a hard problem into branches and solves the leaves. TorchLean does not re-run that search. It checks the leaf record it was handed: are the boxes properly nested, are the arrays the right size, does the claimed lower bound hold?

This is a trust boundary made visible. The expensive search stays outside. The claim that comes back gets checked inside.

Asserts → ok=1, bad=0 for the bundled leaf.

Group D — Does it ever say no?

These two are the most important cases in the suite. A checker that accepts everything looks perfect and proves nothing. Both cases build a broken file at run time, in /tmp inside WSL, and leave your real files untouched.

09
Must reject

neg-tampered

lake exe verify -- lirpa-mlp /tmp/tl_tampered_cert.json

The suite copies the good certificate from case 06 and adds 1000 to its lower bounds. The file is still perfectly valid JSON. Only the mathematics is now a lie.

Lean must catch it. It recomputes, sees that the claimed lower bound of 1230 does not match its own 230, prints both, and refuses the certificate. If this case ever passes silently, the checker has stopped checking.

Rejects → "IBP certificate mismatch", with Lean's numbers and the file's numbers side by side.

10
Must reject

neg-malformed

lake exe verify -- lirpa-mlp /tmp/tl_malformed_cert.json

A different attack: the same certificate cut off after 120 bytes, as a half-finished download would be. The danger is a parser that reads what it can, fills in the rest with defaults, and cheerfully verifies a file that stops mid-sentence.

The failure must land at parse time, before any bound is trusted.

Rejects → "invalid JSON: offset 120: unexpected end of input".

Group E — A bug, and the graphics card

11
Known bug

xfail-pinn-cert

lake exe verify -- pinn-cert

This case is inside out. It passes because the command fails. See A real bug below for what is wrong and what to do about it.

Asserts → the known error text is still present. Turns FAIL when upstream fixes it.

12
GPU · opt-in

cuda-train

lake -R -K cuda=true exe torchlean mlp --device cuda --steps 200

The same Auto MPG training as case 04, moved onto the NVIDIA graphics card. It runs only when you pass --cuda.

It checks two things: the program really says device: cuda, so the work did not quietly fall back to the processor, and the loss still falls. Observed 0.264566 → 0.010684.

This case has a hardware requirement. The driver on this machine, version 592.82, supports CUDA up to 13.1. Toolkit 13.3 compiles but crashes at launch with PTX error 222. Keep the toolkit pinned at 13.1.

Asserts → the line device: cuda appears, and the loss falls.

Section 06

A real bug, found while writing this suite

lake exe verify -- pinn-cert fails on its own bundled example

A PINN is a physics-informed neural network — a model trained to obey a differential equation, not just to fit data. TorchLean ships an example certificate for one, and its README lists the command above as a working example.

It does not work. It throws:

uncaught exception: u(x-h) mismatch at x=0.250000:
Lean (-2.800000, 2.800000) differs from certificate (0.872401, 0.931752)

Read that as: at the grid point x = 0.25, the shipped file claims the network's value lies between 0.872401 and 0.931752. Lean recomputes and gets a far wider range, −2.8 to 2.8. The two disagree, so Lean refuses. Either the file (NN/Examples/Verification/PINN/pinn_cert.json) is stale, or the checker changed under it.

Case 11 records this on purpose. It passes while the bug is present. The day upstream fixes it, case 11 turns FAIL — and that is your signal to read the change and delete the case. A known bug that is tracked is a fact. A known bug that is ignored becomes a surprise.

Section 07

When something fails

What you seeWhat it meansWhat to do
bash: ./run_tests.sh: Permission denied The file is not marked runnable. Type chmod +x run_tests.sh, then run it again.
no checkout at /home/... The script cannot find TorchLean at that path inside Ubuntu. Check the path with wsl -d Ubuntu -- ls ~/TorchLean. Set TL_REPO if it lives elsewhere.
Path has a space The folder name contains a space. Passing it through to Linux would break. Move the folder to a path with no spaces.
The run seems frozen for minutes Normal on a first run. Lean is compiling. Each case has a one-hour ceiling. Wait. The next run of the same case takes seconds.
Case 12 fails, all others pass A GPU or CUDA-toolkit problem, not a TorchLean problem. Confirm the toolkit is pinned to 13.1. After a toolkit change, delete stale .lake/build/*cuda* objects and build again.
Case 11 fails Good news, probably. The upstream PINN bug may be fixed. Run lake exe verify -- pinn-cert yourself and read the new output.
Case 09 or 10 fails Serious. A broken certificate was accepted. Stop trusting the certificate results until you know why. Read the printed output under the FAIL line.

Section 08

Notes for anyone editing the script

A dollar sign does not survive the trip to Linux. When Git Bash launches wsl.exe -d Ubuntu -- bash -lc '...', any $variable inside that text arrives empty. Not an error — empty. The script therefore expands every path on the Windows side and sends plain text across. Keep it that way.

Git Bash rewrites Linux paths. A value like /home/<you>/TorchLean handed to a Windows program becomes C:/Program Files/Git/home/<you>/TorchLean. The script sets MSYS_NO_PATHCONV=1 to stop that. Remove the line and TL_REPO breaks.

Judge by output, never by exit code. Every check greps the command's printed text. This is deliberate, and it is why each PASS line can quote a real number back to you.

Adding a case. Copy the shape of an existing one: run the command into out, test it, call say <name> <0 or 1> "<evidence>". Assert on things that are stable — a count, a message, a falling loss. Do not pin a floating-point number unless the exact value is the point, as in cases 02 and 07.

What is deliberately left out. The full Lean regression suite (lake exe nn_tests_suite), digits-train-certify, and vnncomp-mnistfc. All three are slow or need extra data. Add them when you want a nightly run rather than a 48-second one.
